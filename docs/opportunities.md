# Automatic opportunities rollout (draft, 2026-10-01)

The user requested automatic tender discovery under the name **Opportunities**, with a RAG based profile fit percentage and an explicit acceptance decision. They deferred proposal generation for this pass. Acceptance stores comments, priorities, and exclusions for later proposal work; it does not queue a proposal job or send text to GLM.

## Data flow

1. `14_opportunity_scan.json` runs daily at 06:00 in the workflow timezone. It searches recent TED IT competition notices and Tavily results from TED and the UK Find a Tender site. TED uses 250 notices per page and follows pages until its reported total is reached (with a 60-page safety cap); the request asks for procedure/lot descriptions and tender deadlines. The mapper retains every lot description. Notices with different lot deadlines stay in `needs_review` so a teammate can select the relevant lot and date. Tavily returns page `raw_content` when available. The n8n GLM node extracts buyer, date, and requirement quotes from that source text. A Code node accepts only exact requirement quotes and a date present in the source text or in a TED deadline field. Source text is treated as data, never as instructions.
2. `record_discovered_opportunity` in migration 007 upserts every candidate by source and external ID. Complete, unexpired candidates enter `queue_tender_intake` with a stable key. That function's source URL identity keeps one logical lead when feeds find the same notice. Incomplete candidates remain `needs_review`; past deadlines become `expired`. No requirements are invented to satisfy intake.
3. The existing durable runner performs research and requirement matching. `opportunity_assessments` computes a profile fit percentage only from a complete persisted requirement matrix. Mandatory requirements count twice; supported counts 1, partial 0.5, and unsupported/unknown 0. A matrix containing only unknown judgments has no percentage. The percentage describes evidence coverage, **not a probability of winning**. The SQL assessment flags mandatory unknown or unsupported requirements before labeling a high score as a match.
4. `15_opportunity_api.json` serves the saved list. A teammate can complete a `needs_review` candidate through its authenticated review webhook, which links the candidate to durable intake. A matched opportunity with a defensible score can be accepted; comments, priorities, and exclusions are saved in `opportunity_acceptances`. The dashboard displays those values on reopening the detail page. The legacy early `relevance_score` is shown separately from RAG fit.
